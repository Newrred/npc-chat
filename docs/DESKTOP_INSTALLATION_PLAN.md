# 데스크톱 설치·업데이트·제거 설계

2026-09-29 / Task40 / 기준 앱1.2.0. **설계 완료, 아래 설치기·업데이터는 아직 미구현.** 기존 실행물은 [폴더형 패키지](PORTABLE_DESKTOP.md)다. [의존성과 권리 현황](DESKTOP_DEPENDENCIES.md)을 배포 게이트로 사용한다.

## 현재에서 다음 단계로

현재: 폴더 전체 복사 → EXE → Python/FastAPI + llama.cpp + WebView2 → 별도 AppData 저장. 제거/업데이트는 수동이다.

목표: 설치 화면 → 오프라인 동봉 파일 검증 → 바로가기 → 위젯. 업데이트는 사용자가 받은 새 설치본을 실행하는 방식부터 시작한다. 자동 다운로드/계정/상시 업데이트 서버는 첫 버전 범위에서 제외한다. C#/WPF와 기존 대화 처리는 유지한다.

설치기 도구는 아직 확정하지 않는다. 먼저 현재 C# 환경에서 재사용할 수 있는 설치 트랜잭션/manifest 검증기를 만들고, 설치 UI 도구는 대용량 오프라인 payload·사용자별 설치·제거·라이선스 조건을 확인한 뒤 선택한다. Inno Setup 등 후보를 무료 상용 사용 가능으로 단정하지 않는다. 도구 선택과 서명 인증서는 별도 결정 항목이다.

## 파일과 데이터 배치 (제안)

```text
%LOCALAPPDATA%/Programs/NpcChat/
  Launcher.exe                   고정 바로가기 대상
  current.json                   활성 release ID와 이전 release ID
  releases/<release-id>/          앱 + 런타임 + 그 버전의 모델/자산 전체
  staging/<transaction-id>/       설치 도중, 실행 불가
  install-state.json             소유 파일/작업 단계/복구 정보

%LOCALAPPDATA%/NpcChatDesktop/     현재 데이터 경로 유지
  data/chat.sqlite3              대화·기억·관계
  browser/                       WebView 사용자 저장소/세션 연결 정보
  widget.json                    위젯 설정
  runtime/                       PID 등록·일시 로그, 복원하지 않음
  backups/<transaction-id>/       향후 일관된 데이터 백업
```

기본은 현재 사용자 설치, 관리자 권한/Windows 서비스/시작 프로그램 자동 등록 없음. 다른 사용자 계정은 별도 데이터다. 사용자 지정 설치 경로 지원은 후속이며 첫 버전은 경로 선택을 제한한다. 기존 portable과 같은 데이터 경로를 쓰면 현행 singleton이 중복 실행을 막지만 설치 작업까지 보호하지는 못하므로 설치기와 앱 간 공통 유지보수 잠금이 필요하다.

첫 구현은 버전별 전체 payload를 보존한다. 모델 공유/차등 업데이트는 나중에 도입한다. 약7.8GB 패키지의 새 버전과 이전 버전, 압축 해제 공간 및 데이터 백업이 함께 필요하다. 고정된 여유 공간 수치 대신 manifest의 실제 합계 + 백업 크기 + 추출 임시 크기 + 여유분을 설치 전에 계산한다. 전부 검증하기 전 기존 버전은 삭제하지 않는다.

## 설치와 전환 순서

1. Windows x64·선정한 지원 OS·사용자 권한·디스크 공간 확인. NVIDIA 드라이버/VC++ 필요 여부는 새 PC 검증으로 확정한다. 드라이버를 임의 설치하거나 전체 CUDA Toolkit 설치를 요구하지 않는다.
2. 설치 패키지 출처/서명, manifest 형식·허용 경로·파일 크기·hash 확인. 압축 경로 탈출, 중복/대소문자 충돌, junction/symlink/reparse point를 거부한다. 현재 hash 목록은 서명 인증을 대신하지 않는다.
3. 실행 앱에 정상 종료를 요청한다. 종료되지 않으면 사용자가 앱을 닫고 재시도하게 하고 중단 시 기존 상태를 유지한다. 다른 Python/llama/브라우저 프로세스를 이름으로 일괄 종료하지 않는다.
4. 공통 유지보수 잠금으로 앱 시작도 차단한 상태에서 staging에 새 파일을 완성한다. 중단/전원 종료에 대비해 단계 기록을 저장한다.
5. 업데이트라면 사용자 데이터 일관성 백업과 무결성을 확인한다. 실패하면 전환하지 않는다.
6. 새 버전을 **별도 합성 데이터 디렉터리**에서 smoke 검증한다. 성공한 뒤 같은 볼륨의 완성 release로 이동하고 current.json을 원자적으로 교체한다. 최신 버전 호환 범위/schema를 manifest에 명시한다.
7. 바로가기와 Windows 설치 앱 목록을 등록하고, 최초 실제 사용자 데이터 실행은 migration gate를 통과한 경우에만 한다. ready 확인 후 완료 표시. 기존 정상 버전은 최소1개 보존한다.

향후 manifest에는 app/release ID, 지원 schema 범위, migration 여부, Python/.NET/WebView2/엔진/모델 버전과 출처 revision, 모든 파일 hash, 라이선스 목록 상태, 서명 정보를 둔다. 현재 `package-manifest.json` format1을 완성된 업데이트 계약으로 취급하지 않는다. 빌드 중 wheel도 버전뿐 아니라 hash를 고정하고 오프라인 wheelhouse에서 재현해야 한다.

## 대화 보존과 복구

현재 DB만 남기는 것으로 충분하지 않다. `frontend/app.js`가 WebView localStorage에 profile/session ID를 보관하므로 **browser도 보존**한다. `ChatWindow.cs`의 WebView 경로와 `http://127.0.0.1:8003` origin을 유지한다. 포트나 origin 변경은 별도 세션 이관 기능 없이는 하지 않는다.

업데이트 전 모든 소유 프로세스와 WebView 종료를 확인하고 SQLite backup API로 일관된 DB 사본을 만든다. `PRAGMA integrity_check`와 schema/파일 hash를 검사한다. widget.json과 browser 프로필도 닫힌 상태에서 같은 복구 묶음에 보관한다. 백업 입력은 이 명시적 목록으로 제한하여 backups 자체·runtime PID/로그를 재귀 복사하지 않는다. live sqlite 파일 하나만 복사하거나 WAL/SHM을 무시한 복사를 백업으로 인정하지 않는다. 기존 `scripts/database.py`는 개발용 기능이며 현재 패키지에 없고 위 복구 UI도 없다.

앱 파일 복구와 데이터 복구는 구분한다.

| 실패 시점 | 처리 설계 |
|---|---|
| staging 다운로드/복사/검증/합성 smoke 실패 | 활성 버전과 사용자 데이터 유지, 다음 실행 때 미완료 staging만 식별해 정리 |
| 전환 후 시작 실패, DB/브라우저 변경 없음 | 이전 current로 복귀, 원문 없는 오류 코드 표시 |
| migration 이후 실패 | 새 데이터 보존 사본을 먼저 생성. 이전 앱과 업데이트 전 데이터 묶음을 함께 복원하는 명시적 선택 제공 |
| 업데이트 후 사용자가 새 대화를 저장함 | 예전 백업 자동 덮어쓰기 금지. 잃을 수 있는 데이터 시점을 알리고 취소/현재 유지/백업 복원을 선택 |
| 백업 또는 manifest가 손상됨 | 자동 복구 중단, 양쪽 파일 보존, 안전한 재설치/진단 안내 |

현재 schema 0001이라는 사실만으로 앞으로의 다운그레이드 호환성을 보장하지 않는다. 브라우저 엔진 프로필도 이전 버전과의 호환성을 별도로 검증한다. 백업은 동일 계정/PC 복구용으로 시작하며 다른 PC로 브라우저 프로필 이전을 보장하지 않는다. 백업에 개인 대화가 포함되므로 자동 업로드하지 않는다.

## 제거와 복구 설치

Windows 설치 앱 목록 → 제거 화면 → 소유 프로세스 정상 종료 → 설치 manifest에 기록된 프로그램/바로가기/등록만 제거한다. 기본은 **대화·기억·위젯 설정·백업 보존**. 데이터까지 삭제는 별도 선택과 재확인이 있어야 한다. 백업도 지워진다는 사실을 명시한다. 사용자 지정 `--data-dir` 디렉터리는 자동 탐색·삭제하지 않는다.

삭제 경로는 정규화한 소유 루트 아래인지 검증하고 reparse point를 따라가지 않는다. 사용자 데이터 루트나 상위 폴더를 프로그램 루트로 혼동하면 작업을 거부한다. 파일이 잠기면 전체 완료로 표시하지 않고 남은 파일을 알려 재시도를 제공한다. 재설치 시 보존한 데이터에 다시 연결하고 migration이 필요하면 먼저 백업한다.

복구 설치는 신뢰 가능한 동일 release에서 손상된 프로그램 파일만 재배치하고 데이터는 보존한다. 진단창의 현재 '다시 시도'는 프로세스 재시작 기능이며 설치 파일 복구와 다르다.
