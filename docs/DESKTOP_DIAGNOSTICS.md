# 실행 상태·재시도·진단 파일

Task38, 데스크톱 앱 1.1.0. 위젯 `⋯` 또는 트레이 → **실행 상태 / 문제 해결**에서 확인한다. 시작 실패 시 이 창이 자동으로 열리며 앱을 종료하지 않는다.

## 사용자 흐름

설정 확인 → 포트 확인 → 모델/그래픽카드 확인 → 모델 로딩 → 대화 서버 준비 → 채팅 화면 준비 → 사용 가능 순서다. 특정 단계의 진행률을 추측해 %로 표시하지 않는다.

실패하면 원인에 맞는 안내와 **다시 시도** 버튼이 나온다. 다른 서버가 사용 중인 포트는 임의 종료하지 않고 기존 서버 종료를 안내한다. GPU 메모리 부족이면 다른 GPU 작업 종료를 안내한다. 파일/엔진/구성/시간 초과/접근 권한 오류를 구분하며, 드라이버 또는 DLL 검사 실패처럼 확정할 수 없는 원인은 불확실성을 안내한다.

재시도 전 이 앱이 소유한 이전 프로세스와 채팅 창을 정리하고 새 실행 세션을 만든다. 진행 중 연속 클릭은 무시하며 준비 완료 후 재시작 버튼은 비활성화한다. 대화 DB를 리셋하지 않는다. 진단 창 X는 숨김이고 앱 전체 종료는 기존 트레이/위젯 메뉴에서 한다.

## 내보내기

**진단 파일 저장 (대화 내용 제외)** 버튼을 누르고 저장 위치를 선택한다. 다음 필드만 기록한다.

- 진단 형식 버전, 앱 버전, OS 버전, 64비트 여부, 폴더 패키지 여부
- 최대64개 단계/오류 코드와 앱 시작 이후 경과 초

대화·기억·DB·사용자 이름·경로·환경변수·키·서버 로그·예외 원문은 넣지 않는다. 전체 runtime 로그 폴더를 압축해서 보내는 기능이 아니다. 알 수 없는 예외는 START_FAILED로 정규화한다. 따라서 이 파일만으로 모든 원인을 확정할 수 없고 단계별 추가 점검이 필요할 수 있다.

## 검증

- 기준 상태를 65651a8에 저장, 기준688 Python tests.
- 최종 `./venv/Scripts/python.exe -m pytest -q`: **706 passed**.
- `./venv/Scripts/python.exe -m ruff check app tests scripts`, `./venv/Scripts/python.exe -m compileall -q app scripts`: 통과.
- `./scripts/build-desktop.ps1`: publish 통과. 첫 시도는 실행 중인 이전 앱의 DLL 잠금으로 실패했으며, 해당 앱 종료 후 다시 빌드했다.
- `NpcChat.Desktop.exe --smoke-retry --data-dir <별도 폴더>`: 전용 포트 점유→PORT_BUSY 진단 저장→점유 해제→동시에 두 재시도 요청→한 실행으로 복구→실제 WebView 채팅→표정·403·숨김복원→종료 성공. 개발 실행과 이동된 동봉 패키지 모두 검증했다.
- 내보낸 JSON의 최상위/이벤트 필드가 허용 목록과 정확히 같은지 확인했다. 실패/복구 이력 및 진단 창 캡처는 ignored `.runtime/portable-diagnostics-retry`에 보관했다.
- 동봉 실제9B 모델과 웹 서버가 뜬 뒤 테스트용 네이티브 부모만 강제 종료했다. 감독 프로세스가 두 프로세스를 정리하고 소유 기록을 비웠다. `.runtime/diagnostics-parent-exit-2` 참조.

강제 종료 첫 검증에서는 모델 정리가 남았다. Windows의 닫힌 stdout이 BrokenPipeError 대신 OSError(EINVAL)를 내는 것을 별도 재현했다. `Runtime.stop(..., quiet=True)`를 추가하여 정리 시 부모 출력 연결을 전혀 사용하지 않게 고친 후 실제 모델로 다시 통과했다. 일반 CLI의 종료 메시지는 기존대로 유지한다.

패키지 manifest는 실행 시 재생성되는 Python 캐시를 제외한다. 검사 대상 원본 파일의 동일성 확인이며, 추가 파일 탐지나 디지털 서명을 대신하지 않는다. 감독 프로세스까지 함께 강제 종료/OS 장애인 경우 즉시 정리를 보장하지 않는다. 다른 PC의 첫 실행/드라이버/장시간 검증은 여전히 남아 있다.
