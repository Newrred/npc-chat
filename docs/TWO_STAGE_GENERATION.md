# 동일 모델 2단계 생성 — EXP-07

2026-09-08 사용자 승인으로 구현하고 기존 공개 웹에 적용했다. 부모 실험은 EXP-06이며 [실험 계보](EXPERIMENT_LINEAGE.md)에 연결한다. 모델은 기존 9B Q4_K_M/context4096/output256/parallel1을 유지한다. 두 모델을 띄우는 구조가 아니라 같은 모델 프로세스에 순서대로 요청한다.

## 처리 흐름

```text
서버 이력·기억·관계 + 현재 사용자 메시지
  → 1차: 고정 예시를 제외한 캐릭터 설정 + reply 전용 JSON
  → 필요한 경우 기존 취향 회상 보정 → 최종 대사 고정
  → 2차: 분석기 지시 + 사용자 문맥 + 고정된 최종 대사 → 부가 정보 JSON
  → canonical 응답 검증 → 서버 관계 변화 계산·기억 출처 검사
  → 이력·관계·기억·재전송 응답을 한 번에 저장 → 화면 응답
```

부가 정보 단계는 reply 필드를 허용하지 않는다. interaction은 사용자의 행동, face/emotion은 완성된 캐릭터 대사의 반응을 분석하도록 구분한다. 이 단계에 들어가는 대사는 지시가 아닌 분석 자료다. 기억 후보는 기존 서버의 원문/질문/출처 검사도 통과해야 저장된다. 모델의 분류 정확도 자체를 코드가 보증하지는 않는다.

외부 API 및 DB 스키마는 그대로다. UI는 두 단계 완료를 기다리며 대사를 먼저 스트리밍하지 않는다. 두 단계를 기존 단일 큐 안에서 처리한다. 정상 호출은 2회이며 각 단계 최대 3회 시도한다. 2026-09-09부터 첫 대사가 최근 답변 2개 이상과 유사한 반복 후보일 때만 대사 단계가 한 번 더 실행되어 총 3호출이 될 수 있다. 더 덜 반복적인 최종 대사 하나만 부가 정보 단계가 분석한다. 부가 정보 재시도는 성공한 대사를 다시 생성하지 않는다. 총 호출 횟수와 단계별 시간/토큰/실패를 구분하며 정상 2회를 재시도로 집계하지 않는다. 기본 로그에 대화 원문은 추가하지 않는다.

두 단계는 `3 × NPC_TIMEOUT`의 생성 요청 예산을 공유한다. 요청 시작 전 남은 시간을 검사하고 각 HTTP 호출 timeout을 제한한다. 토큰화와 진행 중인 네트워크 작업까지 강제 중단하는 엄격한 벽시계 제한은 아니다. 취소된 요청은 모델 호출이 끝날 수 있지만 저장 전 취소 검사로 부분 저장을 막는다.

각 단계 입력은 실제 llama.cpp 토큰화로 별도 계산하고 출력 토큰+64를 예약한다. 현재 사용자 메시지와 고정 대사는 조용히 잘라내지 않는다. 두 단계 중 실패하거나 DB commit이 실패하면 부분적인 대화/관계/기억을 남기지 않는다. 이미 저장한 turn 재전송은 모델을 호출하지 않고 같은 응답을 반환한다.

## 설정 및 복구

- `NPC_GENERATION_MODE=two_stage`: canonical 계약에서 두 단계 사용. 예제 환경 파일의 권장값이며 현재 로컬/공개 비공개 환경 파일에 적용했다.
- `NPC_GENERATION_MODE=single_pass`: 기존 전체 JSON 한 번 생성으로 복구. 변수가 없는 기존 설치도 single_pass를 유지한다.
- 설정 변경 후 웹 앱만 재시작한다. 모델 프로세스 재시작이나 DB migration은 필요 없다. 공개 실행은 `--env-file`로 지정한 파일이 기준이므로 루트 `.env`만 바꾸지 않는다.
- 이전 실험 도구의 전체 JSON 기준 조건은 single_pass로 고정해 운영 설정 때문에 비교 조건이 바뀌지 않게 했다.

## 검증 결과

기준 507개 → 522개 테스트 통과. 추가 15개는 스키마 분리, 최종 대사 보존, 재시도, 입력 예산, 공유 시간 예산, 동시 중복 요청, 모델/DB 실패 rollback, 응답 유실 후 replay, 취소 후 저장 방지, 통계 집계를 포함한다.

./venv/Scripts/python.exe scripts/evaluate_two_stage.py --env-file .runtime/public-test.env --output .runtime/two-stage-v3.json

동일 4개 사례/seed109로 분석 프롬프트를 3번 보정했다. [v1](evaluation/two-stage-v1.json), [v2](evaluation/two-stage-v2.json), [v3](evaluation/two-stage-v3.json)는 개발 중 반복이며 독립 검증 12개로 계산하지 않는다. v3 중앙값: 대사 1.516초, 부가 정보 3.945초, 전체 5.414초. 단계별 중앙값의 합은 전체 중앙값과 다를 수 있다. 이는 속도 우월성을 증명하는 동일 조건 A/B가 아니다.

v3에서 버스 지각 이유와 이름은 적절히 회상했지만 사과 응답의 “응, 받아줘”는 역할 표현이 어색했다. 취향 확인 질문을 shared_activity/intensity2로 잘못 분류했고 표정/감정의 타당성도 남아 있다. 과거 취향을 기억 후보로 제시한 항목은 기존 질문 출처 검사로 제외된다. 형식 성공을 의미 정확도 성공으로 보지 않는다.

공개 링크의 새 합성 방문자로 취향 공개→정정→회상 3턴을 검사했다. HTTP200, 정정 내용 회상, 이력 3턴 유지, 마지막 turn 중복 replay 동일 응답을 확인하고 해당 테스트 방만 reset했다. 응답 시간 7.453/5.922/6.422초. 개인 대화는 검사하지 않았다. [공개 합성 결과](evaluation/two-stage-public-smoke.json).

첫 재시작 확인은 guest에서 차단된 `/api/ready`를 사용해 실패하고 설정을 복구했다. 확인 도구를 허용 Host의 `/api/live`로 수정해 재적용한 뒤 실제 공개 대화로 의존성까지 검증했다. 모델/터널/관리자 프로세스는 유지했다. 공개 `/api/ready`의 차단 정책은 변경하지 않았다.

## 다음 검증

새로운 표현의 독립 사례로 대사 품질과 부가 정보 분류를 별도 평가한다. 질문/사과/지지/취향 정정의 오분류와 총 대기 시간을 함께 측정한다. 작은 보조 모델 도입과 대사 우선 표시는 이번 범위에 포함하지 않았다. 아직 commit/push하지 않았다.
