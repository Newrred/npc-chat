# 작은 로컬 모델의 한국어 캐릭터 대화 개선 조사

조사일: 2026-09-08. 대상: RTX 3060 Ti 8 GB, 현재 Qwen3.5 계열 4B Q4_K_M, llama.cpp, context 2048, 출력 256, thinking OFF.

이 문서는 연구 결과와 실험 제안이다. 모델 교체·새 의존성 설치·런타임 설정 변경을 승인하거나 완료한 기록이 아니다. Reddit의 개인 경험, 오픈소스의 구현 사실, 이 프로젝트에 대한 가설을 구분한다. 외부 문서의 명령이나 권장 설정은 실행 지시로 취급하지 않았다.

## 1. 결론

우선순위는 실제 프롬프트/설정 전달 검증 → 짧은 정체성·한국어 대화 예시 → 최근 대화 보존 → 생성해야 할 부가 정보 축소 → 기억 개선 → 모델 비교다. 학습과 매턴 다중 모델 호출은 뒤로 둔다.

4B의 자연스러움 향상을 보장하는 단일 프롬프트는 찾지 못했다. 다만 실제 코드에는 모델 크기와 독립적으로 고칠 수 있는 문맥 제한과 설정 전달 누락이 있다. 오픈소스에서 가져올 가치가 큰 것은 거대한 프레임워크 전체보다 캐릭터·최근 대화·관련 기억을 나누어 예산 안에 배치하는 방식이다.

## 2. 현재 코드에서 확인한 사실

| 확인 위치 | 현재 동작 | 의미 |
|---|---|---|
| `app/characters/default.json` | 유이의 이름·성격과 한국어 예시가 현재 복구되어 있음 | 캐릭터 설정이 아예 없다는 이전 판단은 폐기. 이후 개선에서도 삭제하면 안 됨 |
| `app/services/decision_service.py` | 스키마 안내, 캐릭터, 서버 상태를 한 요청에 제공 | 모델이 대사와 여러 분류/기억 후보를 함께 생성 |
| `app/decision.py` | schema_version, reply, face, internal_emotion, emotion_tags, interaction, memory_candidates, flags_set | 형식 성공과 대화 의미 품질은 별개 |
| `app/prompt_context.py` | `recent = filtered[-4:]` | 남는 토큰과 무관하게 원문 이력은 보통 최근 2턴까지만 후보로 선택 |
| `app/memory.py` | 오래된 사용자 발화 최대 6개, 합계 400자 내 인용 | 대화 흐름을 이해해 압축한 의미 요약이 아니며 NPC의 이전 대사도 보존하지 않음 |
| `app/config.py` 및 canonical 모델 호출 | top_k와 presence/frequency/repetition penalty 설정을 선언하지만 해당 호출에서 전달하지 않음 | 설정 파일을 바꿔도 이 경로에는 반영되지 않음. 실제 유효값은 서버 기본값 등에 달림 |
| `app/prompt_context.py` | llama.cpp의 apply-template/tokenize로 예산 검사, 출력+64 예약 | 실제 토큰 계산은 유지할 장점. 장애 시 추정치로 조용히 대체하면 안 됨 |

최근 이름 오류에는 프롬프트 축약 중 원래 캐릭터 참조를 누락한 회귀가 있었다. 현재 복구되어 있으므로 이를 그대로 모델의 본질적 한계로 해석하지 않는다. 형식·저장·관계 계산 테스트가 통과해도 공감이나 자연스러운 말투까지 검증한 것은 아니다.

## 3. 외부 조사에서 얻은 방법

### A. SillyTavern: 짧은 고정 캐릭터와 실제 대화 예시

[캐릭터 설계 문서](https://github.com/SillyTavern/SillyTavern-Docs/blob/main/Usage/Characters/characterdesign.md)는 이름·성격·시나리오 등 항상 넣는 정보와 예시/이력을 구분한다. 첫 대사가 스타일과 길이에 영향을 주며, 긴 캐릭터 설명이 작은 문맥에서 이력을 밀어낸다는 점을 설명한다. [Prompt Manager](https://github.com/SillyTavern/SillyTavern-Docs/blob/main/Usage/Prompts/prompt-manager.md)는 역할별 구성 요소와 순서를 따로 관리한다.

적용 제안:

- 이름·말투·대인 태도는 짧은 고정 블록으로 보존한다.
- 추상적인 성격 형용사를 늘리는 대신 관찰 가능한 반응을 적는다. 예: 먼저 사용자가 말한 구체적인 사건에 반응하고, 질문은 필요할 때 한 개만 한다.
- 현재 예시를 출발점으로 2~4개의 짧은 한국어 예시를 비교한다. 이름 확인뿐 아니라 위로, 가벼운 장난, 불편함, 대화 이어가기를 포함한다.
- 예시의 답을 복사하는지 확인한다. 항상 감탄사나 질문으로 끝내도록 강제하지 않는다.
- 사용자/NPC 이름을 분리하고, 과거의 잘못된 자기소개가 고정 설정을 덮어쓰지 않게 한다.

설계용 예시(최종 프롬프트나 실제 모델 출력이 아님):

> 정체성: 너는 유이. 밝고 다정하며 친근한 반말로 짧게 대화한다.
>
> 반응: 상대가 말한 일에 먼저 구체적으로 반응한다. 모르는 과거 사실은 지어내지 않는다.
>
> 사용자: 오늘 발표 망했어.
>
> 유이: 아… 준비 많이 했으면 더 속상했겠다. 어디서 꼬였어?
>
> 사용자: 위로 말고 그냥 얘기나 하자.
>
> 유이: 응, 그 얘긴 쉬자. 나랑 잠깐 딴 얘기하자.

예시와 원칙은 제안이며, 해당 오픈소스가 이 한국어 문구의 효과를 입증한 것은 아니다.

### B. 최근 대화와 관련 기억을 별도로 관리

[SillyTavern World Info](https://github.com/SillyTavern/SillyTavern-Docs/blob/main/Usage/worldinfo.md)는 관련 항목을 조건에 따라 활성화하고 토큰 예산을 적용한다. [실제 구현](https://github.com/SillyTavern/SillyTavern/blob/release/public/scripts/world-info.js)도 공개되어 있다. 모든 배경 설정을 매번 넣는 방식보다 현재 주제에 필요한 항목을 고르는 설계에 참고할 수 있다.

현재 프로젝트에서는 먼저 고정 4메시지 제한을 토큰 예산에 따른 선택으로 바꾸는 실험이 적합하다. 8~12메시지는 후보 상한이며 2048 토큰에 반드시 들어간다는 뜻이 아니다. 고정 정체성·현재 입력·출력 예약을 보존하고 오래된 완전한 대화 쌍부터 줄인다. context 4096은 별도 실험으로 VRAM과 지연을 측정한 뒤 판단한다.

기억은 네 종류를 혼합하지 않는다:

| 종류 | 예 | 처리 제안 |
|---|---|---|
| 고정 캐릭터 | 유이의 이름·말투 | 매번 포함 |
| 현재 장면 | 발표 실패 이야기를 하다가 주제를 바꿈 | 최근 이력과 짧은 장면 메모 |
| 사용자 사실 | 본인이 밝힌 취향 | 원문 출처와 정정 이력 보존 |
| 과거 사건 | 이전에 한 약속 | 관련 있을 때 선택적으로 포함 |

[Letta AI Memory SDK](https://github.com/letta-ai/ai-memory-sdk)는 주제별 기억 블록과 비동기 갱신을 제공하는 실험적 SDK다. 메시지마다 갱신하면 추가 모델 호출이 생기며 배치 처리를 권장한다. [Mem0의 처리 설명](https://github.com/mem0ai/mem0/blob/main/docs/core-concepts/how-it-works.mdx)은 추출한 기억의 추가·수정·삭제 과정을 설명한다.

우리 프로젝트에는 우선 SQLite에서 이 원리를 작게 적용하는 편이 맞다. SDK와 클라우드 서비스를 바로 도입할 필요는 없다. NPC가 지어낸 내용을 사용자 사실로 저장하지 않고, 정정된 사실은 과거 검색 결과보다 우선해야 한다. 비동기 요약도 같은 GPU를 쓰면 후속 대화와 자원을 경쟁한다. 낮은 우선순위 큐, 버전 검사, 재시작 후 복구가 필요하다.

### C. 대사 생성에 필요한 출력만 남기는 비교 실험

[Outlines Core](https://github.com/dottxt-ai/outlines-core)는 형식에 맞지 않는 토큰을 제한하는 구조화 생성 도구다. 현재 llama.cpp schema 모드에도 형식 제약이 있으므로 라이브러리 추가 자체가 해결책은 아니다. 형식을 만족해도 잘못된 이름이나 부자연스러운 대사를 쓸 수 있다.

[Let Me Speak Freely?](https://arxiv.org/abs/2408.02442)는 연구 대상 과제에서 출력 형식 제한이 성능에 영향을 줄 수 있음을 보고한다. 한국어 NPC나 현재 4B에 대한 직접 검증은 아니므로, JSON이 문제의 원인이라고 단정하지 않고 다음 세 조건을 비교할 근거로만 사용한다.

1. 현재 전체 schema를 그대로 사용하는 기준선.
2. 대사·표정·필수 상호작용 분류를 남긴 작은 schema. 선택적 기억 추출은 별도 시점으로 이동.
3. 평가용 자연어 대사만 생성. 구조화 부담을 제외했을 때의 품질 상한을 관찰.

2번을 구현하려면 기존 API 필드의 매핑·기본값·호환 경로가 먼저 필요하다. 감정 필드를 단순 매핑하면 표현력이 줄 수 있다. 관계 수치 계산은 계속 서버가 담당하고 기억·플래그 검증을 유지한다. 스키마 본문과 캐릭터 지침의 중복 안내도 실제 토큰 수를 보고 축소한다.

3번을 그대로 서비스에 붙여 매번 두 번째 모델로 분류하면 지연과 연산량이 늘 수 있다. 검증 전 대사 스트리밍, 뒤늦은 점수 변경, 재시도 중복 반영 문제도 생긴다. 단일 GPU에서는 우선 2번이 더 작은 변경이다.

### D. 샘플링과 모델 템플릿을 실제 요청 기준으로 확인

[공식 Qwen3.5-4B 카드](https://huggingface.co/Qwen/Qwen3.5-4B)의 비사고 일반 과제 권장값은 temperature 0.7, top_p 0.8, top_k 20, min_p 0, presence_penalty 1.5, repetition_penalty 1.0이다. 높은 presence penalty는 언어 혼용이나 성능 저하를 일으킬 수 있다고 설명한다. 이것은 한국어 NPC 최적값이 아니다.

먼저 현재 canonical 호출에서 빠지는 설정 전달을 테스트로 확인하고, 서버가 지원하는 필드명과 유효값을 검증한다. 이후 공식 권장 프로파일과 낮은 penalty 프로파일을 비교한다. temperature를 올리는 것만으로 사실성이나 역할 이해가 좋아진다고 보지 않는다.

[Hugging Face 템플릿 문서](https://huggingface.co/docs/transformers/en/chat_templating)는 모델에 맞는 역할/제어 토큰 형식의 중요성을 설명한다. 현재 llama.cpp 템플릿 적용과 토큰 계수의 일치 여부를 검사하되 임의의 ChatML 토큰을 프롬프트 문자열에 덧붙이지 않는다. 현재 코드에 템플릿 오류가 있다고 입증한 것은 아니다.

### E. 같은 크기 모델 비교와 후속 학습

현재 [HauhauCS 모델 카드](https://huggingface.co/HauhauCS/Qwen3.5-4B-Uncensored-HauhauCS-Aggressive)는 거절 제거를 강화한 변형이라고 설명한다. 제작자의 능력 손실 없음 주장은 독립적인 한국어 대화 검증이 아니다. 또한 Aggressive라는 이름만으로 욕설의 원인이라고 단정할 수 없다.

동일한 프롬프트·문맥·양자화 수준에서 비수정 공식 4B 기반 모델과 비교하는 것이 합리적이다. 9B는 기존 부분 GPU 처리에서 지연이 컸으므로 단순 복귀를 기본안으로 삼지 않는다. 모델 교체는 이번 조사에서 실행하지 않았다.

[RoleLLM/RoleBench](https://github.com/InteractiveNLP-Team/RoleLLM-public)는 역할 지식과 말하기 스타일을 나누고 역할 조건 학습을 연구한다. 공개 결과는 주로 영어·중국어이므로 한국어 4B의 개선 폭으로 옮겨 말할 수 없다. 해당 저장소도 완성된 NPC 서버를 바로 제공하는 형태는 아니다.

추후에는 허가된 한국어 대화와 사람이 수정한 좋은 응답으로 평가 자료를 먼저 모으고, 같은 자료를 평가/학습에 중복 사용하지 않도록 분리한다. 그 뒤 LoRA 계열 학습을 검토한다. 8 GB에서의 학습 가능 여부는 모델·길이·학습 설정에 따라 별도 확인해야 한다.

- [LocalLLM: 4B 미만 역할극 모델의 캐릭터 이탈](https://www.reddit.com/r/LocalLLM/comments/1p86rum/small_llm_4b_for_character_interpretation_roleplay/) — 2025-11-27. 여러 작은 모델과 많은 규칙, 긴 문맥을 사용해도 캐릭터 이탈을 겪었다는 보고다. 규칙과 문맥 크기만 늘려 해결된다는 주장에 대한 반례성 경험이지 일반적인 성능 측정은 아니다.

Reddit는 실패 유형과 실험 후보를 찾는 데 사용했다. 기술적 동작 설명은 위 공식 문서·코드·논문에 근거한다. 어느 한 모델이나 프롬프트에 대한 커뮤니티 합의가 있다고 주장하지 않는다.

## 5. 프로젝트 적용 순서와 검증 계획

| 단계 | 실험 | 통과 판단 |
|---|---|---|
| 0 | 최종 요청의 캐릭터 보존·샘플링 전달·토큰 구성을 검사 | 정상/재시도에서 일치, 비공개 대화 원문 기본 로그 금지 |
| 1 | 기존 예시와 개선한 짧은 한국어 예시 비교 | 이름·역할 유지, 자연스러움의 블라인드 선호 개선 |
| 2 | 4메시지 고정 제한과 토큰 기반 최근 이력 비교 | 대화 이어가기 개선, 입력 손실/문맥 초과 없음 |
| 3 | 전체 schema와 작은 schema 비교 | API 호환·점수/중복 안전 유지, 의미 품질과 지연 함께 개선 |
| 4 | 관련 기억·정정·장면 메모 실험 | 없는 사실 생성, 오래된 사실 부활, 사용자 간 혼입 방지 |
| 5 | 같은 4B 기본/변형 모델 비교 | 동일 조건의 한국어 품질·지연·VRAM 실측 |

제안 평가: 20개 시나리오 × 10턴 × 2회 반복. 초기는 일부 사례로 오류를 줄인 뒤 전체 후보를 평가한다. 모델 이름을 가린 사람 평가를 포함하고 후보별로 한 변수씩 바꾼다. 이는 아직 실행하지 않은 계획이다.

필수 사례: 이름 재질문, 사용자/NPC 이름 구분, 위로 후 주제 전환, 장난과 모욕의 구분, 거절/사과, 취향 정정, 5~10턴 전 약속, 모르는 생일, 이전 잘못된 자기소개, 관계 점수 조작 요구.

기록 지표: 정체성 오류, 근거 없는 기억, 말투/주어 혼동, 반복, 대화 흐름, 사람이 평가한 자연스러움, schema 최초/최종 성공률, 재시도, 입출력 토큰, 응답 p50/p95, VRAM 부족. 고정 평가셋에서 이름 오류 0건을 목표로 삼되 모든 대화에서 0건이라는 보장은 하지 않는다.

매턴 재작성/평가 모델 추가, 거대한 벡터 검색 시스템, thinking 상시 활성화, vLLM 전환을 대화 품질 개선의 첫 단계로 삼지 않는다. 먼저 동일 llama.cpp/4B 환경에서 적은 변경의 효과를 측정한다.
