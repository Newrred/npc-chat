# 반복 대사 루프 차단 — EXP-13/14

2026-09-09 Task20 완료. 현재 9B/two-stage/4096 context/256 output/80자 reply/DB/API는 유지했다.

## 실제 증상

명시적으로 활성화된 로컬 추적의 최근 10턴을 읽기 전용으로 확인했다. 7턴에서 “응”으로 시작하는 거의 같은 요구형 대사가 반복됐고, 해당 요청들은 별도 장기 기억을 선택하지 않았다. 마지막 재현 직전 모델 입력 이력은 74개 메시지였다. 사용자 원문과 생성 원문은 이 문서나 평가 파일에 복사하지 않았다.

원인은 최근 assistant 대사가 committed history로 다시 들어가 같은 출력 패턴을 강화한 것이다. 기억 검색 실패와 별개다. 캐릭터 프롬프트에 반복 금지 문구가 있어도 다수의 실제 반복 예시가 입력에 남으면 현재 Aggressive 모델은 이를 계속 따를 수 있다.

## 채택한 동작

- DB 원문은 수정하지 않는다. 대사 생성 단계의 입력 사본만 다룬다.
- 최근 12개 user-assistant pair에서 assistant 대사 유사도 0.70 이상인 군집이 3개 이상이면 첫 pair와 최신 pair만 남기고 중간 pair를 생략한다.
- 형식이 완전한 교대 pair가 아니면 이력을 수정하지 않는다.
- 부가정보 단계는 축약하지 않은 원래 history와 최종 선택된 대사를 받는다.
- 짧은 확인이 아닌 입력에서 첫 후보가 최근 assistant 6개 중 2개 이상과 유사하면 대사만 조건부 1회 재생성한다.
- 두 후보 중 최근 이력 유사도가 더 낮은 후보만 채택한다. 이후 metadata가 그 최종 대사를 분석한다.
- 일반 요청은 기존 reply+metadata 2호출이다. 반복 후보가 검출된 경우에만 reply 재생성으로 총 3호출이 될 수 있다.

## 폐기한 전면 프롬프트 — EXP-13

질문·제안·감정·일반 발화별로 구체적 이유/행동을 요구하고 캐릭터 경계 문구를 추가한 조건을 7사례 × 2조건 × 2seed로 비교했다. 총 28결정/56호출, 형식 오류와 재시도는 없었다.

- 활동 제안은 구체화됐다.
- 개방형 도움 질문의 명확한 개선은 1/2뿐이었다.
- 감정 사례에 알려지지 않은 준비 노력과 다음 합격을 단정하는 답이 생겼다.
- 의견 사례에는 불필요한 질문·학교 상황 추측이 붙었다.
- 경계 사례 2/2에서 명확한 거부에 실패했고 한 답변은 오히려 더 하라는 방향이었다.
- 합성 반복 이력에서는 기존 조건도 반복을 재현하지 않아 이력 축약 효과를 판정할 수 없었다.
- 전체 시간 중앙값 OFF 7.148초, ON 9.273초. 순차 소표본이라 고유 지연 차이로 단정하지 않는다.

따라서 전면 지침과 캐릭터 경계 문구는 기본 프롬프트에서 제거했다. 평가 harness에서만 재현할 수 있고 운영에는 적용하지 않는다. 원자료: [EXP-13 합성 결과](evaluation/reply-quality-v1.json).

## 실제 반복 이력 비저장 재현 — EXP-14

마지막 실제 문제 턴을 DB에 쓰지 않고 이전 history와 함께 다시 생성했다. 사용자 원문/답변 원문은 저장하지 않고 이력 수, 반복 유사도, 호출 단계만 집계했다.

| seed | 기존 history | 반복 축약 적용 |
|---:|---|---|
| 109 | 최근 답변 유사도 1.000, 유사 답변 4개 | 5 pair 생략, 유사도 0.400, 유사 답변 0개 |
| 211 | 최근 답변 유사도 0.714, 유사 답변 2개 | 5 pair 생략, 유사도 0.400, 유사 답변 0개 |

적용 조건 두 번 모두 정상 reply+metadata 2호출만 사용했고 조건부 재생성은 필요하지 않았다. 별도 재실행에서도 둘 다 경계/중단 표현을 포함했으나 “응”으로 시작했다. 따라서 반복 루프 탈출은 확인했지만 일반적인 답변 깊이와 캐릭터 주체성 전체가 해결됐다는 뜻은 아니다. DB 쓰기·공개 요청·일일 quota 소비는 없었다.

## 검증 과정

초기 Task20 단위 실행은 5실패/29통과였다. 유니코드 정규화된 `ㅇㅇ` 인식, 실제 한국어 문장 유사도 기준, 자연스러운 한 번의 반복에 대한 과민 재생성 문제가 원인이었다. 짧은 확인을 정규화하고 임계값을 실제 점수에 맞추며 최근 유사 응답 최소 2개 조건을 추가했다. 후속 1실패는 테스트 후보가 두 과거 대사 중 하나와만 임계값을 넘은 것으로, 실제 검출 조건에 맞는 후보로 수정했다. 실패를 skip하지 않았다.

합성 모델 실험: `scripts/evaluate_reply_quality.py --env-file .runtime/public-test.env --output docs/evaluation/reply-quality-v1.json`. 실제 반복 재현은 무시된 `.runtime` 보조 도구로 실행했고 원문·출력을 저장하지 않았다.

평가 JSON은 28행/56모델 호출, parse/transport 실패 0건으로 다시 확인했다. 웹과 관리자만 재시작하고 모델·터널·DB는 유지했다. 공개 합성 방문자에서 root/session/chat/reset이 모두 HTTP 200이고 답변이 비어 있지 않음을 확인한 뒤 해당 합성 대화를 reset했다. 로컬 주소에서 public guest session을 직접 여는 첫 시도는 접근 경계에 따라 403이었으며, 실제 공개 주소를 사용한 검증으로 교정했다.

## 한계와 다음 단계

문자 유사도는 의미가 같은 완전한 바꿔 말하기를 모두 찾지 못하며, 우연히 비슷한 문장을 반복으로 볼 수 있다. 그래서 3개 이상 군집과 최근 2개 이상 후보 조건을 사용한다. 반복 재생성은 최악의 경우 모델 호출 하나만큼 응답을 늦춘다.

이번 채택은 반복 루프 차단에 한정된다. 단발성의 얕은 맞장구까지 안정적으로 개선하려면 현재 모델의 전면 프롬프트를 더 붙이기보다, 더 적합한 instruct/roleplay 모델 비교 또는 현재 두 호출을 계획→대사 구조로 재설계하는 별도 실험이 필요하다.
