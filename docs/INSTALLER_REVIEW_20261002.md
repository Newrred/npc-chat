# 설치기 정밀 검증과 용량 최적화 — 2026-10-02

기준 `b351574`, 설치기 0.1.0/앱 1.4.0. 사용자는 설치기의 문제 여부를 꼼꼼하게 확인하고 크기를 줄일 방법을 요청했다. 기존 4070 Ti 기록과 사용자 AppData, 원본 ZIP/패키지는 보존했다. 새 산출물은 `1.4.0-review-20261002` 내부 검증용이며 외부 업로드/커밋/푸시는 수행하지 않았다.

## 발견 및 수정

1. **앱 payload 무압축:** DLL/소스까지 ZIP_STORED로 담아 불필요하게 컸다. app.zip에 Deflate level 6을 적용하고 바깥 ZIP은 이미 압축된 app.zip과 원본 모델을 그대로 저장한다. 설치기 EXE만 바깥 ZIP에서 추가 압축한다. 모델 양자화/가중치/동봉 런타임 파일은 변경하지 않았다.
2. **설치 후 캐시 중복:** 성공해도 전체 app.zip과 모델이 cache에 남았다. 검증과 활성화 성공 뒤 이번 release의 두 hash 캐시만 정리한다. 실패/취소 때는 이어받기 캐시를 보존한다. 새 회귀 검사는 수정 전에 이 조건에서 실패했고 수정 후 통과했다.
3. **실패/취소 임시 폴더 누적:** 현재 시도가 만든 staging만 finally에서 정리한다. 모든 하위 경로를 먼저 검사하고 junction/symlink를 거부하며, 다른 시도의 폴더는 삭제하지 않는다. 이미 확보한 캐시 바이트를 여유 공간 계산에 반영해 재시도 때 전체 다운로드 공간을 또 요구하지 않는다.
4. **동명 바로가기 덮어쓰기:** 기존 `NPC Chat.lnk`의 대상이 다르면 보존하고 안내하도록 변경했다. 같은 대상이면 사용자 설정도 유지한다. 실제 COM 바로가기를 테스트 폴더에 생성하고 바이트가 유지되는지 확인했다. 개인 바탕화면 바로가기는 건드리지 않았다.
5. **입력/취소 경계:** null payload 항목을 잘못된 설치 정보로 거부하고, 이미 취소된 호출은 폴더 생성 전에 중단한다.

정리 실패(파일 잠금/권한 등)는 검증된 설치를 되돌리지 않으며 임시 파일이 남을 수 있다. 강제 프로세스 종료/전원 차단으로 finally가 실행되지 않은 옛 staging을 자동으로 지우는 기능은 추가하지 않았다.

## 검사 결과와 범위

기준선은 Python722개/설치 핵심26개와 빌드 통과였다. 변경 후 Python **723개**, 설치 핵심 **64개**, Ruff/compileall 및 설치기 publish가 통과했다. 설치 핵심 검사에서 302 거부의 예외가 기존 테스트 보조 함수의 허용 목록에 없어 한 번 중단됐으며, `HttpRequestException`도 기대한 네트워크 실패로 처리한 뒤 통과했다. 제품이 리디렉션을 허용하도록 바꾼 것은 아니다.

| 영역 | 확인한 내용 |
|---|---|
| 정상/재시도 | 신규 설치, 같은 버전 재시도, release 이동 후 current 기록 전 중단을 모사한 복구 |
| 변경 제한 | 다른 버전 업데이트 거부, 손상 manifest/파일 검증, 잘못된 payload 구성 거부 |
| 취소 | 시작 전 취소, 파일 준비 중 취소, 추출 후 모델 복사 직전 취소, 비활성 상태 유지, 캐시 재사용 |
| 정리 | 성공 시 해당 payload 캐시 제거, 취소 시 자기 staging만 제거, 다른 staging sentinel 보존 |
| 동시 실행 | install.lock을 가진 다른 설치가 있을 때 거부 |
| 경로/압축 | 상대 경로 탈출, 절대 경로, 예약 이름/ADS, 대소문자 중복, ZIP symlink 항목, app.zip 내부 모델, 해제 크기 초과, manifest 누락 거부 |
| 다운로드 | 206 이어받기, 200 재시작, 잘못된 Range/짧은 응답/302/HTTPS 강등 거부, 같은 길이의 손상 캐시 재다운로드 |
| 오프라인 | 로컬 payload 부분 복사 이어받기, 크기 오류/경로 오류 거부 |
| 바로가기 | 테스트 폴더에 실제 .lnk 생성, 같은 대상 보존, 다른 대상 거부 및 원래 파일 바이트 보존 |
| 빌더 | 앱 압축 후 바이트 일치, 모델 원본 유지, 새 manifest에 고지 포함, payload hash/크기 일치, 바깥 ZIP 중복 압축 회피 |

다운로드 응답은 합성 HttpMessageHandler로 검증했다. 실서비스 HTTPS 호스팅/실제 네트워크 끊김은 검증한 것으로 취급하지 않는다. 실제 저용량 디스크를 채우거나 전원을 차단하지 않았다.

## 실물 산출물

9월29일에 이전된 전체 9B 패키지를 입력으로, 수정된 빌더와 설치기로 새 오프라인 ZIP을 생성했다. 고지 40개를 포함하고 권리 검토 미완료 상태를 유지한다.

| 항목 | bytes / 십진 GB |
|---|---|
| 기존 기록의 오프라인 ZIP | 7,888,794,545 / 7.89GB |
| 새 오프라인 ZIP | **6,765,167,878 / 6.77GB** |
| 감소 | **1,123,626,667 / 약 1.12GB (14.24%)** |
| 앱 payload 압축 전 파일 합계 | 2,121,355,503 / 2.12GB |
| 압축 app.zip | 1,079,315,152 / 1.08GB |
| 원본 model.gguf | 5,627,044,224 / 5.63GB |
| 성공 후 제거되는 payload 캐시 합계 | 6,706,359,376 / 6.71GB |
| 빈 캐시 기준 설치 디스크 여유 요구 | 14,991,630,015 / 약 15.0GB |

위 여유 요구는 설치 디스크의 캐시+staging+여유분이다. 사용자가 보관하는 운반 ZIP/압축을 푼 설치 원본과 .NET의 시스템 임시 추출물은 별도다. 설치된 앱 자체는 약7.75GB로 유지되며 다운로드 압축과 설치 용량을 혼동하지 않는다. 같은 입력을 무압축 저장했을 때의 ZIP 크기도 archive metadata로 계산하면 7,888,794,517bytes로 기존 기록과 거의 같다.

새 ZIP SHA256: `a99b6326d4f7dd06be514bc7e91195c82191efc460865dcc21986021de30eb2c`.

모델 SHA256: `2ca636d9e81d3d23ca9b60c234fe185d30ec082eeba69ce770fdb0c76559a4f5` (원본 그대로).

최종 ZIP을 실제로 풀면서 CRC를 확인했고, Windows TEMP를 작업 디렉터리로 설정해 한글·공백이 포함된 새 경로에 `--install-test`로 설치했다. **종료코드0, success=true, executable=true**, 설치 시간 **158.546초**였다. cache/staging이 비어 있음을 확인했고 동봉 Python 검증기도 `valid=true`, 변경/누락 없음으로 통과했다. `--preview`로 실제 WPF 설치 화면을 렌더링하여 설명/버튼/진행바가 보이는 것을 확인했다. 마우스로 일반 설치 버튼을 누르는 전체 UX 검증과는 구분한다.

**설치 후 실제9B 채팅은 이번 부하 상태에서 실패했다.** 서버 준비와 WebView2 실행까지 진행됐지만 약120초의 채팅 관찰 한도 내 응답을 받지 못해 `Chat UI failed`, 종료코드1이 기록됐다. 웹 로그에는 `llm_transport_failure`가 남았다. 모델 실행 중 관찰값은 GPU 전체11397MiB 사용/600MiB 여유/100% 활용률이었다. 모델 종료 후에도7405MiB 사용/81% 활용률이 관찰돼 다른 GPU 작업 부하가 있었다. 다만 이 관찰만으로 실패 원인을 확정하지 않는다. 사용자가 “현재 부하 상태로 결과 기록”을 선택해 다른 프로그램을 종료하거나 낮은 부하로 재시험하지 않았다.

실패 후 소유 registry는 `{}`이고 해당 설치 경로의 실행 프로세스가 없음을 확인했다. 설치된 파일의 물리 합계는 실제 실행 후 Python 캐시를 포함하여7,761,538,289bytes였다. 9월29일 별도 패키지에서 성공했던 실제9B 검사와 이번 실패를 구분한다. 설치 성공을 현재 부하에서의 원활한 모델 실행 보장으로 확대하지 않는다.

이어 같은 설치본을 별도 데이터 경로에서 `--smoke-widget --no-topmost`로 실행한 **합성 응답 UI 검사는 종료코드0**으로 통과했다. 실제 WebView2/FastAPI에서 채팅·표정·빠른 답장·미리보기·숨김/복원·창 제어를 검사하고 캡처를 확인했다. 모델 응답은 가짜이며 실제 추론 성공 근거로 사용하지 않는다. 소유 registry `{}`와 잔존 프로세스 없음도 확인했다.

## 추가로 줄일 선택지

- **현재 적용:** 파일 내용 변경 없는 앱 압축과 성공 후 캐시 정리. 기본 오프라인 사용과 모델 품질을 유지한다.
- **다운로드형 배포:** 사용자가 처음 받는 EXE는 현재 약140MB이지만, 이후 앱/모델 약6.71GB를 받아야 한다. 총 전송량이나 설치된 모델 크기가 없어지는 방식은 아니다. 실제 호스팅 주소는 미정이다.
- **오프라인 원본 직접 읽기:** 로컬 동봉 payload를 캐시로 먼저 복사하는 단계를 줄이면 설치 중 디스크 사용/복사를 더 줄일 여지가 있다. 읽는 동안 원본 이동/변조/분리 및 재시도 계약을 검증해야 하며 이번에는 도입하지 않았다.
- **작은 모델 선택:** 설치 용량의 가장 큰 부분은5.63GB 모델이다. 4B 또는 다른 양자화는 별도 품질·속도·8GB 장비 비교가 필요하다. 이번 최적화에서는 모델을 바꾸지 않았다.
- **런타임 공유:** 설치된 WebView2/.NET을 활용하는 별도 경량 배포는 검토할 수 있지만, 동봉 환경과 별도 설치 없는 오프라인 실행이라는 전제가 달라진다. 브라우저/DLL 파일을 임의 삭제하지 않았다.

## 남은 제품 게이트

신규 설치와 같은 release 재시도 범위의 검증이다. 버전 업데이트·제거/앱 목록 등록·손상 설치 수리·코드 서명·실제 온라인 배포·깨끗한 Windows·네트워크 차단·장시간/절전 복귀·권리 확정은 남는다. 따라서 판매용 설치기에 문제가 전혀 없다는 판정은 아니다.

## 재현 명령과 증거

```powershell
./venv/Scripts/python.exe -m pytest -q
./venv/Scripts/python.exe -m ruff check app tests scripts
./venv/Scripts/python.exe -m compileall -q app scripts
# desktop 디렉터리에서
../.runtime/dotnet/dotnet.exe run --project SetupChecks -c Release
# 저장소 루트에서
./venv/Scripts/python.exe scripts/build_installer.py --package <이전한-9B-패키지> --output <새-출력> --release-id 1.4.0-review-20261002
# 최종 ZIP을 푼 뒤
./NPCChatSetup.exe --preview <새-PNG>
./NPCChatSetup.exe --install-test <한글과-공백이-포함된-새-폴더>
# 설치된 앱에서
./runtime/python/python.exe scripts/verify_desktop_package.py .
./NpcChat.Desktop.exe --smoke-real --no-topmost --data-dir <별도-테스트-데이터>
git diff --check
```

산출물과 build-result/release/manifest는 ignored `.runtime/installer-review-20261002/`, 실물 설치 캡처와 결과는 `.runtime/installer-review-checks-20261002/`에 보존한다. C# 소형 fixture는 출력에 표시된 Windows TEMP의 전용 GUID 폴더에 남는다. 개인 대화 DB를 읽거나 수정하지 않았다.

검증 뒤 빌드 중간 app.zip/model.gguf 복사본과 테스트용 운반 ZIP 해제 폴더의 삭제를 시도했으나 자동 승인 검토가 명령 실행을 차단했다(구체적 사유 미제공). 따라서 이 중복 복사본 약13.55GB는 남아 있다. 설치 엔진 자신의 캐시 정리 검사는 별개이며 실제 설치에서 통과했다. 최종 ZIP, 설치된 테스트 앱, 캡처/결과/manifest/release/build-result 및 원본 패키지도 보존돼 있다.
