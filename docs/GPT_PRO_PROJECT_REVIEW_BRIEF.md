# GPT Pro 프로젝트 검토 브리프

검토 기준일: **2026-09-21 (KST)**  
기준 저장소: **`Newrred/npc-chat`의 `main`**

이 문서는 저장소 링크를 외부 AI 검토에 전달할 때 현재 구현과 과거 계획을 혼동하지 않도록 만든 진입점이다. `docs/handoff-package/`는 2026-09-03 당시의 역사적 스냅샷이며 현재 상태를 설명하는 문서가 아니다.

## 1. 지금 구현되어 있는 제품

- 모바일 중심의 캐릭터 채팅 UI에서 **유이**와 **띳띠**를 선택해 대화한다.
- FastAPI 한 프로세스가 정적 프런트와 `/api`를 같은 주소에서 제공한다.
- LLM 추론은 별도 OpenAI-compatible `llama.cpp` 프로세스가 담당한다.
- 관계 수치, 대화, 기억, 중복 요청 방지는 SQLite에 영속 저장한다. 기본 실행에 Redis는 필요 없다.
- 서버가 대화 이력과 상태의 기준이며 브라우저가 보낸 이력·점수·기억을 신뢰하지 않는다.
- 정적 표정 이미지를 기본으로 사용한다. ComfyUI는 선택 기능이며 현재 코어 흐름에서는 꺼져 있다.
- 로컬 검사창에서 실제 모델 입력·출력, 기억 검색·저장 판단, 두 단계 생성 과정을 확인하고 테스트 프롬프트를 임시 편집할 수 있다. 검사창과 상세 추적은 공개 앱에 노출하지 않는다.

## 2. 현재 요청 처리 흐름

```text
브라우저
  -> FastAPI guest/session 검증과 서버측 한도 확인
  -> SQLite에서 해당 사용자·캐릭터의 확정된 대화와 상태 조회
  -> 최근 대화, 구조화된 사용자 정보, 출처 있는 사건, 관련 장기 기억 구성
  -> llama.cpp에 대사 전용 JSON 생성 요청
  -> 같은 모델에 확정 대사를 기준으로 표정·감정·기억 후보 분석 요청
  -> Pydantic 검증
  -> 서버의 결정론 규칙으로 5개 관계 수치 계산
  -> 한 트랜잭션으로 대화·관계·기억 저장
  -> 답변과 정적 표정 이미지를 브라우저에 표시
```

두 번째 모델이나 별도 분류기는 없다. 현재는 같은 9B 모델을 두 번 순차 호출하며, 대사 성공 뒤 메타데이터 재시도가 필요해도 성공한 대사를 다시 생성하지 않는다. 출력은 두 단계가 끝난 뒤 사용자에게 전달한다.

## 3. 현재 로컬 실행 프로파일

- 장비: Intel i7-11700, RAM 약 32 GB, RTX 3060 Ti 8 GB
- 현재 시험 모델: Qwen3.5 9B Aggressive 계열 Q4_K_M
- 문맥: 4096, 출력 상한 256, 동시 추론 1, batch/ubatch 128, thinking OFF
- 빠른 복구 후보: 4B Q4_K_M, context 8192, GPU all
- 모델 1개, 앱 worker 1개, 생성 큐 1개를 유지한다.

2026-09-21 읽기 전용 운영 점검에서 모델·웹·로컬 검사창·Quick Tunnel은 약 239시간 연속 실행 중이었고 DB 무결성, 외부 생존 응답, CPU·RAM·GPU 상태에 이상이 없었다. 실제 대화 사용량은 적었으므로 이 결과는 동시 사용자 부하 검증을 대신하지 않는다.

## 4. 기억과 문맥의 현재 방식

- 최근 이력은 고정 턴 수가 아니라 실제 토큰 예산 안에서 확정된 턴을 뒤에서부터 선택한다.
- 이름·선호 호칭처럼 명시적인 사용자 정보는 원문 근거를 가진 구조화된 뷰로 전달한다.
- 추천·제안·약속·취소는 발화 주체와 원문 근거를 보존해 일반 기억 후보와 구분한다.
- 최근 화제의 전환·종료·취소를 고려해 과거 사건을 보수적으로 선택한다.
- 기억 후보는 주체가 불명확하거나 근거가 없으면 저장하지 않는다.
- 최신 완전한 대화 한 쌍을 일반 기억보다 먼저 문맥에 보존한다.

이 구조는 이름과 명시적 추천·약속 회상을 개선했지만 모든 암시 표현과 복잡한 장기 사건 연결을 해결하지는 못했다. 검색 재현율, 잘못된 과거 화제 선택, 긴 대화에서의 정보 압축은 계속 평가해야 한다.

## 5. 확인된 강점과 품질 한계

강점:

- 대사와 메타데이터를 나눈 뒤 단일 응답 생성보다 역할 혼동과 형식 실패가 줄었다.
- SQLite 저장, 캐릭터별 상태 분리, 새로고침 이력 복원, 중복 요청 방지가 구현되어 있다.
- 합성 평가 자료와 실험 계보가 저장소에 남아 있어 채택·폐기 이유를 추적할 수 있다.
- 한 명령으로 전체 로컬/임시 공개 구성을 시작·중지·재시작할 수 있다.

한계:

- 9B 모델은 구체적인 제안이나 긴 대화의 알맹이보다 짧은 맞장구로 흐를 때가 있다.
- 두 번의 순차 추론 때문에 답변 지연이 늘어난다.
- 규칙 기반 기억 검색은 설명 가능하고 빠르지만 다양한 간접 표현의 의미 검색에는 한계가 있다.
- 현재 실험은 합성 사례와 소규모 실사용 중심이며, 블라인드 사람 평가와 동시 부하 자료가 충분하지 않다.
- 인터넷 검색과 외부 도구 호출은 아직 대화 흐름에 연결하지 않았다.

## 6. 배포 상태와 운영 전 남은 게이트

현재 외부 테스트는 도메인 없는 Cloudflare Quick Tunnel과 자동 서명 guest cookie를 사용한다. 이메일 로그인 없이 링크로 접속할 수 있고 서버측 일일 한도와 분당 제한을 적용한다. 이 구성은 임시 테스트용이며 실제 운영 배포가 아니다.

운영 전에 최소한 다음이 남아 있다.

1. 고정 도메인과 named tunnel 또는 동등한 고정 reverse proxy
2. 재부팅 자동 시작, 비정상 종료 자동 복구와 상태 알림
3. 대화·기억·usage DB의 정기 백업, 보관 기간, 사용자 삭제 기능
4. 실제 동시 사용자 부하와 긴 연속 대화 검증
5. 오류율·응답 지연·큐 대기시간·GPU 상태의 지속 관측
6. 공개 서비스에 필요한 신고·차단·콘텐츠 운영 정책
7. 저장소 라이선스와 캐릭터 이미지 사용 권한 정리

브라우저에서 LLM 포트에 직접 접근하는 경로는 없고 Quick Tunnel은 FastAPI만 가리킨다. 로컬 검사창은 loopback 전용이다.

## 7. GPT Pro에 요청할 검토 범위

다음 질문에 답하도록 요청하는 것이 좋다.

1. 현재 3060 Ti와 단일 사용자 PC 서버 제약에서 **다음 세 작업의 우선순위**는 무엇인가?
2. 호출 횟수를 더 늘리지 않으면서 대사의 구체성·자연스러움·문맥 회상을 개선할 방법은 무엇인가?
3. 현재 규칙 기반 기억과 토큰 예산 문맥을 유지하면서 의미 검색을 어디까지 추가하는 것이 적절한가?
4. 동일 모델 2단계 생성을 유지할지, 한 단계 구조화 출력이나 더 작은 메타데이터 모델로 바꿀지 어떤 실험으로 판단할 수 있는가?
5. 임시 공개 테스트에서 소규모 운영 서비스로 넘어갈 때 가장 먼저 해결해야 할 장애·데이터·보안 위험은 무엇인가?
6. 기존 실험 자료로 결론 내릴 수 있는 것과 새로 수집해야 하는 평가 자료는 무엇인가?

제안은 대규모 재작성보다 현재 FastAPI·정적 프런트·SQLite·별도 llama.cpp 구조를 기준으로, 작고 되돌릴 수 있는 단계로 요청한다.
